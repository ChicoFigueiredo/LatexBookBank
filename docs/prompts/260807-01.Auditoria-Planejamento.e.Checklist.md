# Prompt — Revisão Arquitetural do LatexBookBank após Planejamento Inicial

## Contexto

Trabalhem sobre o repositório:

`ChicoFigueiredo/LatexBookBank`

Os documentos atuais que devem ser considerados a fonte de verdade do planejamento são:

* `docs/_atual/_planejamento.md`
* `docs/_atual/_checklist.md`

O levantamento e planejamento realizados até aqui estão aprovados como base.

**Não refaçam o planejamento do zero.**

O objetivo deste prompt é incorporar um novo conjunto de decisões arquiteturais antes do início das fases principais de desenvolvimento, principalmente para garantir que o aplicativo continue excelente como aplicação local, mas possa posteriormente evoluir para uma aplicação web/SaaS sem reescrita estrutural.

---

# 1. Decisão arquitetural principal

O LatexBookBank deve continuar sendo desenvolvido como:

> **LOCAL-FIRST, CLOUD-READY.**

Isso significa que o ambiente principal de desenvolvimento e autoria continuará inicialmente utilizando:

* Next.js;
* TypeScript;
* SQLite;
* filesystem local;
* TeX Live local;
* `pdflatex`;
* `pdftocairo`;
* Ollama/local AI quando desejado.

Não migrar agora o ambiente principal para Vercel/PostgreSQL.

Ao mesmo tempo, nenhuma regra de domínio poderá depender diretamente de:

* SQLite;
* filesystem local;
* TeX instalado na máquina;
* Ollama;
* Vercel;
* Neon;
* Vercel Blob.

Esses componentes devem ser considerados **providers de infraestrutura**, e não partes intrínsecas do produto.

---

# 2. PostGIS está explicitamente fora do projeto

## Decisão definitiva

**NÃO USAR POSTGIS.**

PostGIS está fora de questão e não deve:

* aparecer no planejamento;
* aparecer no schema;
* aparecer como dependência;
* aparecer como possibilidade futura;
* ser utilizado para bounding boxes;
* ser utilizado para crops;
* ser utilizado para posições em páginas;
* ser utilizado para layout de documentos.

Os dados espaciais encontrados no LatexBookBank são coordenadas de documentos, e não dados geográficos.

Um recorte deve ser representado com campos normais.

Exemplo:

```ts
interface SourceAnchor {
  id: string;
  sourceAssetId: string;

  pageNumber: number;

  xNormalized: number;
  yNormalized: number;
  widthNormalized: number;
  heightNormalized: number;

  rotation?: number;

  cropAssetId?: string;
}
```

Utilizar preferencialmente coordenadas normalizadas entre `0` e `1`.

Exemplo:

```text
x = 0.18342
y = 0.31527
width = 0.51431
height = 0.08791
```

Isso permite reconstruir o crop independentemente de:

* DPI;
* resolução;
* tamanho da imagem;
* tamanho do preview.

# 7. Regras para portabilidade SQLite → PostgreSQL

Manter desde a Fase 0:

* UUID para IDs novos;
* `workspaceId` onde fizer sentido;
* timestamps UTC;
* constraints explícitas;
* índices documentados;
* repository boundaries;
* evitar SQL raw espalhado;
* nenhuma regra de negócio dependente de comportamento particular do SQLite;
* testes de domínio independentes do provider.

Não é necessário que as migrations SQLite e PostgreSQL sejam literalmente as mesmas.

É aceitável ter estratégias de migration específicas.

O requisito importante é:

> o domínio e os use cases não devem precisar ser reescritos.


# 14. Upload de arquivos grandes

Na futura versão cloud:

Evitar:

```text

  ↓
Next.js Function
  ↓
Storage
```

para PDFs e assets grandes.

Preferir:

```text
Browser
  ↓
upload direto autorizado
  ↓
Object Storage
```

O servidor deve:

1. autenticar;
2. autorizar;
3. fornecer mecanismo/token de upload;
4. registrar posteriormente os metadados no banco.

Isso reduz:

* memória;
* tráfego interno;
* risco de timeout;
* custo de functions.

```text
                    LATEXBOOKBANK

            ┌────────────┴────────────┐
            │                         │
         DOMÍNIO                  APPLICATION
            │                         │
            └────────────┬────────────┘
                         │
                    PROVIDERS

         │               │                │
      DATABASE        STORAGE          RENDER
         │               │                │

                         │
                         │
                        AI
                         │
                  OpenAI-compatible
                  / Ollama / remoto
```

O objetivo é que:

> **SQLite seja uma implementação, e não o LatexBookBank.**

> **Uma pasta seja uma implementação, e não o LatexBookBank.**

> **Vercel seja uma implementação, e não o LatexBookBank.**

> **Neon seja uma implementação, e não o LatexBookBank.**

> **Ollama seja uma implementação, e não o LatexBookBank.**

O produto é o domínio editorial, o banco de questões, os assets, a proveniência, o editor LaTeX, o renderer, a árvore, o agente e as regras de negócio.

A infraestrutura deve poder mudar ao redor disso.
