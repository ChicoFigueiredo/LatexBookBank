# 1. Avaliação geral

A direção arquitetural atual está aprovada:

> **LOCAL-FIRST, CLOUD-READY**

O modo local deve continuar sendo produto de primeira classe e não apenas ambiente temporário de desenvolvimento.

A arquitetura deve permitir:

```text
MODO LOCAL

Next.js
  +
SQLite
  +
LocalFileStorage
  +
Renderer Docker local
  +
Ollama / IA local
```

e futuramente:

```text
MODO CLOUD

Next.js / Vercel
  +
PostgreSQL
  +
Object Storage
  +
mesmo Renderer Docker hospedado remotamente
  +
AI Provider remoto
```

As regras de negócio não devem saber qual desses ambientes está sendo utilizado.

# 2. Decisões consideradas corretas e aprovadas

Permanecem aprovadas as seguintes decisões.

## 2.1 SQLite como banco principal local

Aprovado.

```text
Prisma
   ↓
SQLite
```

é a implementação principal durante o desenvolvimento inicial e para o modo local.

PostgreSQL continua sendo alvo futuro e será validado no Cloud Compatibility Spike.

---

# 2.2 PostgreSQL/Neon como candidato cloud

Aprovado.

Neon pode ser utilizado como primeiro PostgreSQL cloud a ser testado.

A aplicação não pode depender de funcionalidades exclusivas do Neon.

---

# 2.3 PostGIS

Decisão definitiva:

# ❌ POSTGIS NÃO ENTRA NO PROJETO

Não utilizar PostGIS:

* para crops;
* bounding boxes;
* páginas;
* layouts;
* regiões;
* SourceAnchor;
* OCR.

Coordenadas de documentos devem continuar utilizando números normalizados entre `0` e `1`.

---

# 2.4 StorageProvider

Aprovado.

Implementação inicial:

```text
LocalFileStorageProvider
```

Candidato cloud:

```text
VercelBlobStorageProvider
```

Possibilidade futura:

```text
S3StorageProvider
```

Nenhum SDK concreto de storage pode vazar para o domínio.

---

# 2.5 SourceAnchor

Aprovado integralmente.

Manter:

```ts
interface SourceAnchor {
  id: string;
  sourceAssetId: string;

  pageNumber: number;

  xNormalized: number;
  yNormalized: number;
  widthNormalized: number;
  heightNormalized: number;

  rotation?: number;

  cropAssetId?: string;
}
```

O `SourceAnchor` representa a origem lógica do conteúdo.

O crop continua sendo armazenado como artefato derivado útil.

---

# 2.6 Asset imutável

Aprovado.

Arquivos de origem devem ser tratados como patrimônio editorial.

Se um arquivo mudar:

> criar outro Asset.

Não sobrescrever silenciosamente o anterior.

O `sha256` continua sendo central para:

* identidade;
* integridade;
* auditoria;
* cache;
* histórico;
* comparação.

---

```text
109 MB
```

Portanto storage não é atualmente um risco econômico relevante.

A deduplicação também não precisa ser prioridade.

O hash continua importante por integridade e proveniência, não por economia de espaço.

# 3. Ajuste obrigatório 1 — contrato App ↔ Renderer ↔ Storage

Este é o ajuste arquitetural mais importante desta rodada.

Existe atualmente uma incompatibilidade conceitual entre:

```text
renderer sem rede de saída
```

e:

```text
renderer gravando artefatos via StorageProvider cloud
```

Se o renderer não possui acesso externo, ele não pode enviar diretamente arquivos para Vercel Blob ou outro object storage remoto.

## Decisão

O renderer deve ser:

# STORAGE-AGNOSTIC

Ele não deve conhecer:

* Vercel Blob;
* S3;
* filesystem da aplicação;
* banco;
* Workspace;
* Prisma.

---

# 4. Novo fluxo do renderer

Utilizar:

```text
Next.js
   │
   │ RenderBundle
   ▼
Renderer Docker
   │
   ├── PDF
   ├── PNG
   ├── diagnostics
   ├── stdout
   └── metadata
   │
   ▼
Next.js
   │
   ▼
StorageProvider
```

O renderer recebe apenas o necessário para compilar.

---

# 5. RenderBundle

Criar um contrato semelhante a:

```ts
interface RenderBundle {
  jobId: string;

  sourceLatex: string;

  profile: string;

  assets: RenderAsset[];

  options: RenderOptions;
}
```

Os assets necessários para a compilação podem ser enviados:

* via multipart;
* tar/zip;
* stream;
* mecanismo equivalente.

A decisão concreta pode ser tomada durante a Fase 6.

---

# 6. RenderResult

Algo equivalente a:

```ts
interface RenderResult {
  success: boolean;

  pdf?: Uint8Array;
  png?: Uint8Array;

  diagnostics: RenderDiagnostic[];

  stdout?: string;
  stderr?: string;

  durationMs: number;
}
```

O renderer não persiste o resultado definitivamente.

A aplicação recebe o resultado e decide:

```text
StorageProvider.put(...)
```

---

# 7. Consequências positivas

Isso permite manter o container:

```text
sem rede de saída
```

e ainda utilizar:

```text
LocalFileStorage
```

ou:

```text
Vercel Blob
```

sem alterar o renderer.

Também mantém a imagem Docker idêntica entre local e produção.

---

# 8. Ajuste obrigatório 2 — separar Backup do Renderer

O renderer deve ter uma responsabilidade extremamente pequena:

> compilar LaTeX.

Não colocar lógica de backup dentro do processo `renderer`.

---

# 9. Arquitetura recomendada no host remoto

Pode existir:

```text
Droplet
│
├── latex-renderer
│
└── latexbookbank-backup-job
```

Ou:

```text
Droplet
│
├── renderer container
├── backup container
└── scheduler/cron
```

O fato de os dois rodarem no mesmo host não significa que devem pertencer ao mesmo serviço.

---

# 10. Responsabilidade do backup

O backup deve reutilizar:

```text
PortableArchive
```

e gerar:

```text
.lbb
```

Aprovada a decisão de fazer:

> backup = mesmo formato da exportação.

Isso evita formato de restauração paralelo.

---

# 11. Ajuste obrigatório 3 — `.lbb` não pode ser simples espelho do schema runtime

O formato `.lbb` é uma ótima decisão.

Manter:

```text
biblioteca.lbb
├── manifest.json
├── data.sqlite
└── assets/
```

Entretanto, existe um detalhe importante.

Não definir:

```text
data.sqlite = cópia direta permanente do schema Prisma atual
```

O formato `.lbb` precisa sobreviver à evolução interna da aplicação.

---

# 12. Criar um schema portátil versionado

Fluxo recomendado:

```text
Runtime Domain
      ↓
Export Projection
      ↓
Portable Schema v1
      ↓
data.sqlite
```

Futuramente:

```text
Runtime Domain v8
      ↓
Export Projection
      ↓
Portable Schema v2
```

Isso permite que:

* Prisma mude;
* migrations mudem;
* SQLite vire PostgreSQL;
* nomes internos mudem;

sem destruir compatibilidade de arquivos `.lbb`.

---

# 13. manifest.json

Manter:

```json
{
  "formatVersion": 1
}
```

e evoluir explicitamente quando necessário.

O importador deve possuir migradores de formato quando fizer sentido.

Exemplo:

```text
LBB v1
 ↓
LBB v2
 ↓
Runtime atual
```

Nunca adivinhar versões desconhecidas.

---

# 14. Ajuste obrigatório 4 — rever a frase “quatro providers e apenas quatro”

A intenção está correta, mas a redação pode causar interpretação equivocada.

Hoje existem naturalmente outros contratos:

```text
QuestionTypePlugin
MathRecognitionProvider
QuestionSearchService
PortableArchive
QuestionPatch
```

Isso não é abstraction hell.

---

# 15. Nova redação recomendada

Substituir:

> Quatro fronteiras de provider, e apenas quatro.

por:

> **Quatro fronteiras primárias de infraestrutura.**

São elas:

```text
Persistence / Repository
StorageProvider
RenderExecutor
AiProvider
```

Essas são as quatro grandes fronteiras externas do runtime.

Outras interfaces de domínio continuam permitidas quando representam comportamento real.

---

# 16. Regra contra abstrações desnecessárias

Manter explicitamente:

Não criar:

* interfaces para classes que nunca terão outra implementação;
* factories sem necessidade;
* abstrações de uma linha;
* DI framework pesado;
* service locator;
* microserviços por módulo.

Pergunta de controle:

> Existe mais de uma implementação real ou um boundary arquitetural importante?

Se não:

> provavelmente não precisa de interface.


Não criar o diretório antecipadamente sem uso.

# 25. Segurança do renderer

Manter obrigatoriamente:

* diretório temporário por job;
* timeout;
* CPU limit;
* memory limit;
* sem `shell-escape`;
* sem comando construído como string;
* `execFile`/`spawn` com argumentos;
* filesystem efêmero;
* nenhum acesso ao banco;
* nenhuma credencial cloud;
* nenhuma API key de IA;
* sem rede de saída quando tecnicamente viável.

# 29. Aprovação do `.lbb`

A ideia está aprovada.

Formato conceitual:

```text
workspace.lbb
├── manifest.json
├── data.sqlite
└── assets/
    └── xx/
        └── sha256.ext
```

Requisitos:

* checksums;
* `formatVersion`;
* round-trip;
* validação;
* nenhuma sobrescrita silenciosa;
* assets por hash;
* independência de path;
* schema portátil versionado.
